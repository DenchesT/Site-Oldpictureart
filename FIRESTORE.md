# Правила безопасности Firestore

Отметки «в избранное» хранятся в Firestore. Ключ в `docs/firebase-config.js`
публичный — так и задумано, он не секрет: файл отдаётся браузеру каждого
посетителя, иначе сайт не смог бы обратиться к базе. Доступ ограничивают
не ключом, а правилами на стороне Firebase.

**Пока правила не настроены, коллекцию `likes` может переписать кто
угодно, у кого открыт сайт.** Это единственное место во всей затее, где
чужой человек может что-то испортить.

## Что вставить

Firebase Console → ваш проект → **Firestore Database** → вкладка
**Rules** → заменить содержимое и нажать **Publish**:

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {

    // Отметка — это документ на пару «человек + картина».
    // Читать может кто угодно: счётчик виден всем.
    // Писать — только вошедший, только от своего имени и только
    // в документ со своим идентификатором.
    match /likes/{likeId} {
      allow read: if true;

      allow create, update: if request.auth != null
                    && likeId == request.auth.uid + '_' + request.resource.data.postId
                    && request.resource.data.userId == request.auth.uid
                    && request.resource.data.keys().hasOnly(['userId', 'postId', 'createdAt']);

      allow delete: if request.auth != null
                    && resource.data.userId == request.auth.uid;
    }

    // Всё остальное закрыто
    match /{document=**} {
      allow read, write: if false;
    }
  }
}
```

### Почему create и update разрешены вместе

Сайт ставит отметку вызовом `set()`. Для правил `set()` — это создание,
если документа не было, и изменение, если он уже есть. Отдельная строка
`allow update: if false` выглядела строже, но ломала повторную отметку
той же картины: человек видел «сохранено только в этом браузере» и не
понимал почему. Условия у обеих операций одинаковые, так что строже от
запрета ничего не становилось — чужую запись всё равно не тронуть, и
лишнего поля в свою не подложить.

## Как устроены записи

```
likes/<uid>_<postId>
    userId     — тот же uid, что в имени документа
    postId     — номер записи (атрибут data-post-id у кнопки-сердечка)
    createdAt  — время сервера
```

Ровно три поля, ни одним больше: правило `hasOnly` отказывает в доступе,
если в записи окажется что-то ещё. Снятая отметка — это удаление
документа, а не поле `liked: false`; поэтому мусора в базе не копится.

Если правила когда-нибудь перестанут совпадать с тем, что пишет сайт,
это будет видно сразу: в консоли браузера появится
`Missing or insufficient permissions`, а человеку сайт скажет, что
отметка сохранена только в этом браузере. Посмотреть настоящий вид
записей можно в Firestore Database → Data, проверить правило, не ломая
живые данные, — там же во вкладке **Rules** → **Rules Playground**.

## Заодно проверьте два пункта в консоли Firebase

1. **Authentication → Sign-in method.** Входа через Google на сайте
   больше нет — только почта и пароль. Провайдер **Google** здесь можно
   выключить, **Email/Password** должен оставаться включённым. В
   **Settings → Authorized domains** пусть будет `oldpictureart.ru`:
   по этому списку Firebase проверяет ссылки из писем для сброса пароля.

2. **Google Cloud Console → APIs & Services → Credentials → ваш ключ.**
   В списке разрешённых должны быть только сервисы Firebase. Если туда
   случайно попал посторонний платный API — например Generative Language
   или Maps, — публичным ключом смогут жечь ваши квоты. Там же полезно
   ограничить ключ по источнику: Application restrictions → HTTP
   referrers → `oldpictureart.ru/*` и `denchest.github.io/*`.
